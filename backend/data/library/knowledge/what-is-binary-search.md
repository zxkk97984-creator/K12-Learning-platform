# 从猜数字游戏说起

经典游戏：心里想一个 1 到 100 的数，对方来猜，只回答「大了」或「小了」。乱猜平均要五十次；但若每次都猜剩余区间的正中点，最多七次必然命中——因为 2⁷ = 128 > 100。每猜一次排除一半候选，这个策略就是二分查找，它是计算机科学中最优雅的算法之一。

# 前提与流程

二分有一个不可妥协的前提：数据必须有序。道理很直白——「目标比中间元素小就丢弃右半区」这条推理，只在有序序列上成立；乱序数据的中点两侧毫无规律，砍掉哪一半都可能把目标一起扔掉。

流程用伪代码描述不过数行：设左右指针圈住候选区间；当左端不超过右端时循环——取中点与目标比较：相等则命中返回；中点小于目标则左指针移到中点右侧；否则右指针移到中点左侧。循环结束仍未命中则确认不存在。每一轮候选规模严格减半。

# 对数级的威力

减半的效率用数字感受最直接：一千条数据约十步，一百万条约二十步（2²⁰ ≈ 10⁶），十亿条约三十步。数据规模扩大一千倍，代价只多十步。这种对数级增长曲线对比线性扫描的「数据翻倍、时间翻倍」，高下立判。

日常你早已受益于它：数据库索引让亿级记录毫秒响应，底层是有序结构上的查找；调试程序时「注释一半代码定位问题」的二分法，也是同一思想的生活版。

# 边界是二分的天敌

二分的思想一分钟就能讲明白，写对却需要功夫——难点全在边界。左指针和右指针何时更新？循环条件用「小于」还是「小于等于」？中点取偏左还是偏右？任何一处差一，都会漏掉元素或陷入死循环。

程序员的通行做法是用不变量思考：始终明确「目标一定在左右指针之间（如果存在）」这句话在每个时刻都成立，再据此决定每一步怎么走。写出实现后，还要专门测试三种边界：目标是最小值、最大值、以及不存在于数组中的情况。想清楚边界，才算真正学会二分。

# 一笔划算的账

如果数据本来无序，先排序再二分划算吗？排序要付出 O(n log n) 的成本。答案取决于查询次数：只查一次，线性扫描更省；若要查询一万次，排序成本被摊薄成万分之一，之后每次都享受对数速度，总账大赚。这叫摊销思想——一次性投入，长期摊销回报。

最后留一个思考题：有人把全班成绩排好序后用二分找自己的名次，为什么这是用错了工具？提示：二分找到的是「与目标相等的元素位置」，而名次需要的是「大于等于该分数的人数」，两者不是同一个问题。选对算法之前，先想清楚你要回答的问题是什么。
