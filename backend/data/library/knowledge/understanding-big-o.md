# 秒表为什么靠不住

想比较两个算法谁快，第一反应是各跑一次掐秒表。但这把尺子问题很多：机器性能、编程语言、系统负载都会干扰结果；更麻烦的是数据规模一变，结论可能整个反转——小数据下简单的冒泡排序甚至常快过归并，大数据下却被远远甩开。我们需要一把只看算法本身、不受环境影响、还能预测规模变化后表现的尺子。

# 大 O 在数什么

这把尺子叫时间复杂度，用大 O 记号表示。做法是：数出算法基本操作次数关于输入规模 n 的表达式，丢掉常数系数，丢掉低阶项，只保留增长最快的领头项。n(n−1)/2 次操作记作 O(n²)；3n + 5 次记作 O(n)；n·log₂n + 100 记作 O(n log n)。

丢得这么狠看似粗暴，实则精准。我们真正关心的问题是：数据扩大十倍百倍后，谁先崩溃？在这个问题上，常数无关紧要，增长形状才是一切。「这趟车两小时级别」而不说「119 分钟」——大 O 就是这样说话的。

# 五个必须认识的形状

把常见复杂度排成一条队伍：O(1) < O(log n) < O(n) < O(n log n) < O(n²)。O(1) 是数组按下标取值，一步到位；O(log n) 是二分查找，每次砍一半；O(n) 是从头扫一遍；O(n log n) 是高效排序的成本地板；O(n²) 是双层循环的蛮力，再往后就是指数爆炸的灾难区。

配一个体感数字：假设每秒十亿次操作。n 为一百万时，O(n) 耗时毫秒级，O(n²) 要半小时起步。工程经验法则由此而来：小数据怎么写都行，海量数据下能否降到线性或线性对数，常常决定架构生死。

# 空间也有复杂度

时间不是唯一的账本，内存占用同样用大 O 描述，叫空间复杂度。归并排序需要一块与数据等大的临时空间，记作 O(n)；冒泡排序原地交换，只需常数个临时变量，记作 O(1)。内存紧张的场景（比如嵌入式设备）里，空间复杂度常常比时间更金贵。

于是「空间换时间」成为算法设计的经典交易：用查表代替计算、用索引代替扫描，都是在花空间的钱买时间的速度。好的工程师做选择前会先问三个问题：现在最缺的是时间还是空间？数据规模会涨到多大？这笔交易的回报能持续多久？

# 两点严谨性

其一，大 O 描述的是增长上界的趋势，不预测绝对耗时：常数巨大的 O(n) 算法在小规模上完全可能输给 O(n²)。其二，同一算法有最好、最坏、平均之分——快排平均 O(n log n)，最坏却退化为 O(n²)，高风险场景更要盯最坏情况。

掌握大 O 之后，你就获得了一种纸上谈兵的超能力：不用运行程序，读代码的结构就能估算性能——单层遍历标 O(n)，嵌套双层标 O(n²)，范围每轮减半标 O(log n)。先看形状、再看细节、最后才谈微优化，这是分析一切性能问题时永远不会出错的正确顺序。
