# 调试是工程的核心工作

外行以为工程师每天都在创造新东西，真相是：他们大部分时间在找错、定位错、修复错。硬件项目尤其如此——代码、电路、机械三个层面互相影响，任何一个环节的小毛病都会让整台机器行为异常。调试（debug）因此不是附带技能，而是核心能力。

# 五步调试循环

成熟的调试方法是一个循环：预测——运行前先写下「我预期会发生什么」；观察——实际运行并如实记录现象；对比——找出预期与现实的差异；定位——根据差异推断问题出在哪一层；修改——只改一处，再回到预测。五步一圈，圈数越多机器越接近可靠。

每轮只改一处是铁律。同时调整三个参数后性能变了，你永远不知道是哪个改动起了作用；下次再出问题时，也没有干净的参照系可回退。

# 硬件调试的三层排查法

机器人出了故障，按固定顺序逐层排查能少走弯路。第一层查供电：电池电压够吗？开关真的开了吗？线材有没有松脱？大量「诡异故障」其实是接触不良。第二层查连接：马达插在几号口？传感器线序对不对？接口与程序编号一一对应了吗？第三层才查程序：逻辑条件写反了吗？边界值处理了吗？从物理层往上查，符合「简单原因更常见」的经验规律。

# 日志是最被低估的工具

人脑记不住八轮实验中哪个参数对应哪个结果。准备一张调试日志表：版本号、改动内容、预期效果、实测表现、下一步计划，每次实验填一行。它能在迷雾中提供唯一确定的事实链，也是向老师和队友说明思路的最佳材料。职业工程师的调试日志往往比代码本身更有长期价值。

# 心态也是调试力

硬件调试对心态的考验不亚于技术。连续三小时找不到问题时，沮丧和自我怀疑会涌上来，而烦躁恰恰是排查的大敌——它会让你跳步、误判、乱改一通。成熟工程师的应对是主动管理节奏：卡壳超过四十分钟就起身喝水散步，换双手再来；或者找队友复述一遍问题——很多 bug 在向别人描述的过程中自己现形。记住调试圈的最后一环永远是心态复位：问题一定有原因，只是还没被看到。

# 动手实践

给你的小车故意埋一个故障（比如把左马达线换到右马达口），然后严格按五步循环排查：先预测症状，再运行验证，逐层检查直到定位。全程记录日志。完成后复盘：哪一步浪费了最多时间？下次哪个动作可以更早执行？会复盘的调试者，成长速度是别人的数倍。


# 二分法定位大法

分享一个排查利器：当问题可能出在多个环节时，用二分法快速缩小范围。比如小车不动，先检查一半的可能性——通电正常吗？正常的话，马达直接测试转不转？转的话就是程序问题，不转就是线路问题。每次检查都排除一半嫌疑，三四步就能锁定病灶。这种对半切分的思路和查找算法里的二分思想一脉相承——调试本身也是一门算法。
