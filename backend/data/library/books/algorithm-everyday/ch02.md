T: 排序的艺术：从冒泡到归并

S: 最直觉的方法：冒泡
P: 五份试卷散乱地摆在桌上，要按分数从低到高排好，你会怎么做？多数人的第一反应是冒泡排序的思路：从头开始，比较相邻两份，顺序不对就交换；扫完一轮，最高分必然「浮」到末尾。重复几轮，直到某整轮没有任何交换发生为止。|mark:冒泡排序
@kp=sorting-algorithm
KC: 排序算法 :: 排序算法把一组按任意顺序存放的数据重排成指定顺序。评价它主要看比较与移动的次数随数据量增长的速度。:: 生活里的例子 · 扑克牌理牌时把最小的不断往前换，就是人肉版冒泡排序。
P: 用伪代码写出来只需两层循环——外层控制轮数，内层负责相邻比较与交换。动手在纸上推演一组五个数据的排序，你会发现一个规律：第一轮最多 n-1 次比较，第二轮 n-2 次……总比较次数约为 n(n-1)/2。当 n 是 100 时约五千次；当 n 变成一百万时，约五千亿次。
P: 五千亿是什么概念？即便计算机每秒完成十亿次比较，也要将近一小时。而现实中数据库动辄十亿级记录，靠冒泡显然不行。注意问题不出在「思路错误」——它完全正确，只是增长速度太吓人。这引出了本章真正的主角：能否让步数增长得更慢？
CALL: 想一想 :: 冒泡排序有一处天然优势：如果数据本来就基本有序，第一轮几乎不发生交换，很快就能提前收工。想想什么场景下这个优点很值钱？

S: 分而治之：归并登场
P: 归并排序换了一个视角：别盯着相邻两个比，先把整堆数据一分为二，各自排好，再把两份有序的小堆合并成一份有序的大堆。小堆怎么排？继续对半拆，拆到只剩一个元素——单个元素天然有序。然后逐层合并回来。这就是分治策略：化整为零，各个击破。|mark:归并排序
P: 精华全在合并这一步。两堆已排好的试卷怎么合成一堆？比较两堆最顶上的两张，小者抽出放到新堆，如此往复——每抽一张只花一次比较，合并 n 张纸至多约 n 次比较，线性时间搞定。
FIG: 一棵自顶向下的二叉树：顶部是无序数组 [38, 27, 43, 10]，向下分裂为单元素节点，再向上逐层合并，每个合并节点旁标注「线性合并」，树高标注 log₂n 层 :: 归并排序的分解与合并：拆只要对半砍，合只需线性扫描，代价是层数只有对数层
P: 数一数总账：拆分加合并共约 log₂n 层，每层合计约 n 次操作，总量约 n·log₂n。代入刚才的数字：一百万个数据约两千万次操作，不到半秒就能完成——对比冒泡的一小时，快了上万倍。算法之间的差距，不在常数，而在增长的形状。
P: 归并的优雅还体现在稳定可预期：无论输入数据原本多么混乱，它都按同样的节奏拆分合并，成绩几乎不受运气影响。这种稳定性在需要「最坏情况也有保证」的场合格外值钱。
P: 公平起见也说说归并的代价：合并时需要一块额外空间暂存结果，空间开销是 O(n)；冒泡则可以原地腾挪，几乎不占额外内存。世上少有免费的午餐，「用空间换时间」是算法设计中反复出现的交易，第四章我们会把这桩生意算得更细。
KC: 分治策略 :: 分治策略把大问题切成规模更小的同类子问题，分别解决后再合并结果。拆分要容易，合并要有清晰的做法。:: 生活里的例子 :: 全班大扫除时按区域分组打扫，最后一起验收，把干净的教室「合并」回来。
CALL: 动手推演 :: 在纸上对 [5, 2, 8, 1] 完整走一遍归并过程，标出每一次合并发生的比较次数，核对总数是否符合你的预期。

S: 小结与预告
P: 回顾本章：冒泡直观但步数随 n² 增长，大数据下不可行；归并用分治把复杂度压到 n·log₂n，代价是额外空间；算法间的差距本质是增长形状的差距。你已经隐约摸到了那把尺子的轮廓。
P: 排序解决「让混乱变有序」，但更多时候我们只想在一大堆数据里找到某一个。有序的数据里找东西能有多快？下一章的二分查找会给你一个违反直觉的答案：一百万条数据，最多二十次。
