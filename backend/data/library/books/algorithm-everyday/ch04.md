T: 度量快慢：时间复杂度与大 O

S: 秒表为什么不可靠
P: 想比较两个排序谁快，第一反应是各跑一次掐秒表。但这把尺子问题很多：机器性能不同、语言不同、当天负载不同，测出来的秒数没有可比性；更麻烦的是数据规模一变，结论可能整个反转——小数据下冒泡甚至常快过归并（启动开销小），大数据下却被碾压。我们需要一把只看算法本身、不看运行环境的尺子。
@kp=time-complexity
KC: 时间复杂度 :: 时间复杂度刻画算法基本操作次数随输入规模 n 增长的趋势，用大 O 记号表示，忽略常数系数与低阶项，只保留增长最快的那一项。:: 生活里的例子 · 说「这趟车是两小时级别」而不说「119 分钟」，忽略细节保留量级，正是大 O 的说话方式。
P: 大 O 的做法看似粗暴，实则精准：数出操作次数关于 n 的表达式，丢掉常数系数，丢掉低阶项，只留增长最快的领头羊。n(n-1)/2 次 → O(n²)；3n + 5 次 → O(n)；n·log₂n + 100 → O(n log n)。为什么要扔得这么狠？因为我们关心的是「数据扩大十倍百倍后谁先崩溃」，常数在这个问题上无关紧要。

S: 常见等级的直觉
P: 把常见复杂度排成一条队伍：O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(2ⁿ)。O(1) 是数组按下标取值，数据再多也一步到位；O(log n) 是二分查找；O(n) 是从头扫一遍；O(n log n) 是高效排序的地板；O(n²) 是双层循环的蛮力；指数级则是灾难区，n 到五十就已宇宙热寂级别。
P: 给每个等级配一个体感数字：假设每秒十亿次操作。n 等于一百万时，O(n) 耗时毫秒级，O(n²) 要半小时起步，O(2ⁿ) 根本等不到结果。所以工程界有条经验法则：竞赛或作业里写出 O(n²) 无伤大雅；生产系统面对海量数据时，能否降到线性或线性对数常常决定架构生死。
P: 两点严谨性补充。其一，大 O 描述的是增长上界的趋势，不预测绝对耗时——O(n) 的算法若常数巨大，小数据下完全可能输给 O(n²)，所以「复杂度低」与「实际快」在小规模处可以背离。其二，同一算法还有最好、最坏、平均之分：快速排序平均 O(n log n)，最坏却会退化为 O(n²)，工程选型时最坏情况往往更要命。

S: 复杂度思维的实际用法
P: 掌握大 O 后，你获得了一种纸上谈兵的超能力：读一段代码的结构就能估出它的复杂度，不必真跑。看到单层循环遍历 n 个元素，心里标 O(n)；循环里套循环且内外都依赖 n，标 O(n²)；每次循环把范围减半，标 O(log n)。这种静态分析能力让你在写代码之前就预判性能瓶颈。
P: 它也改变你优化问题的切入点。遇到卡顿的程序，第一问不是「哪里能抠几个毫秒」，而是「整体是什么形状」——若是 O(n²)，任何微优化都救不了它，必须换算法；若已是 O(n log n)，再谈常数层面的精打细算才有意义。先看形状再看细节，这是性能工作的正确顺序。
P: 最后把前几章串起来：归并的 n·log₂n 与二分的 log₂n 不再只是两个数字，而是两种增长形状的名字；「空间换时间」也不再是一句口号——归并多花 O(n) 空间换来对蛮力的降维打击。下一章我们把权衡艺术推向更烧脑的领域：当问题连「一步步来」都行不通时怎么办？

CALL: 动手分析 :: 用本章方法估一估你最近写的任一段代码的时间复杂度：找出最深的嵌套层数，判断每层的循环规模，给出一个大 O 结论并说明理由。

S: 小结与预告
P: 回顾本章：秒表受环境干扰不可靠；大 O 忽略常数与低阶项，只留增长的形状；常见等级从 O(1) 到 O(2ⁿ) 各有体感；复杂度分析能在写代码前预判瓶颈。度量的问题解决了，但有些问题的困难不在「慢」，而在候选方案多到数不过来。
P: 最后把前几章串起来看：归并的 n·log₂n 与二分的 log₂n 不再只是两个孤立的数字，而是两种增长形状的名字；「空间换时间」也不再是一句口号——归并多花 O(n) 的空间，换来对蛮力方法的降维打击。概念一旦连成网，记忆就再也跑不掉了。
