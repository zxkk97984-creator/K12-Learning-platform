T: 分而治之：MapReduce 与海量计算

S: 一道算不动的统计题
P: 任务：统计整个互联网所有网页里，「北京」这个词一共出现了多少次。假设网页总量一百亿个，平均每个一兆字节——总数据量达到一万万亿字节级别。用一台顶级服务器逐页扫描，需要跑上几十年。这道题难的不是算法，而是规模：单打独斗的时代结束了，必须让一万台机器一起上——这套方案就叫 MapReduce。|mark:MapReduce
@kp=mapreduce-paradigm
KC: MapReduce 范式 :: MapReduce 把大任务拆成两个阶段：映射阶段各机器独立处理数据块并输出键值对，归并阶段按键聚合结果；框架自动调度与容错。:: 生活里的例子 :: 全班统计选票：每人先数自己手里的票（映射），组长再汇总各组票数（归并）。

S: 两个阶段的分工
P: 映射阶段的纪律是「各扫门前雪」：数据被切成上千块分发下去，每台机器只处理自己那块，输出一批键值对。统计词频的任务里，读到「北京」就吐出一张纸条写着「北京，1」；读到「上海」就写「上海，1」。机器之间零通信、零依赖——正因为互不干扰，才能放心地并行一万份。
P: 归并阶段接手这些纸条，规则只有一条：相同键的放在一起求和。所有「北京，1」汇到某台机器加成「北京，八百多万」；「上海」同理。两阶段之间有个自动完成的搬运环节（按 键 分组），工程师甚至不用关心它怎么实现。整个统计从几十年缩短到几分钟。
P: 用伪代码表达极简：「映射函数接收一个文档，对其中每个词输出该词计数为一的键值对；归并函数接收同一个词的所有计数，输出它们的求和」。至于切分数据、分发任务、按键分组、汇总输出这些脏活，全部由框架自动完成。程序员只需要写好映射与归并两个函数。

P: 程序员只需要写好「映射」与「归并」两个函数，剩下的脏活——调度、传输、失败重试——全部由框架代劳。这个设计让普通开发者也能驾驭千机集群，是它改变云计算历史的真正原因。

S: 容错：一万台机器必然坏几台
P: 集群越大，故障越日常。一万台机器连续跑几小时，期间有几台死机几乎是必然事件。MapReduce 的容错哲学简单粗暴：任何一台机器挂了，它负责的数据块重新找台健康机器从头再算一遍。因为映射任务是纯函数——同样输入必得同样输出——重算没有任何副作用，安全无比。
P: 这背后是一个深刻的设计取舍：放弃「永不宕机的超级机器」幻想，转而拥抱「会坏的普通机器加聪明的容错软件」。与其花天价追求百分之九十九点九九的单机可靠，不如接受百分之九十五的单机可靠再用冗余把它堆到整体接近完美。分布式系统的全部智慧，都始于这次观念转身。
KC: 纯函数与容错 :: 映射任务是纯函数——相同输入必得相同输出且无副作用，因此任何机器故障只需换机重算即可自动恢复，这是分布式容错的基石。:: 试一试 :: 解释为什么「掷骰子」不适合当映射任务。
CALL: 动手模拟 :: 和四位同学模拟一次单词计数 MapReduce：一人当框架分发报纸剪页，四人各自统计自己那页的词频纸条，最后一人按键归拢求和。记录总耗时与出错重试次数。

S: 小结与预告
P: 回顾本章：映射阶段无通信并行、归并阶段按键聚合，程序员只写两个函数；纯函数特性让故障重算天然安全；从「造不坏的机器」到「容忍坏机器的聪明软件」，是分布式时代的观念革命。
P: 四个伟大算法已经集齐：PageRank 教我们从关系读价值，Dijkstra 教我们贪心扩张，RSA 教我们用数学不对称守护信任，MapReduce 教我们拥抱并行与容错。最后一章，把它们放在同一张桌上，看看伟大设计的共同气质。
