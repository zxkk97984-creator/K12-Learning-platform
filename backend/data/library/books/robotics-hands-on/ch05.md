T: 赛场实战：循线竞速挑战

S: 比赛规则与策略空间
P: 决战开始。赛道：白底黑线的环形跑道，含直角弯与缓弯，全程约四米。规则：从起点出发沿黑线跑完全程，冲出线需从出界处重新上线，用时最短者胜。注意规则留下的策略空间——它只约束「沿线跑」，没规定怎么跑：速度策略、过弯路线、修正参数全都由你做主——这场竞速比的是谁把车调得更聪明。|mark:竞速

KC: 调试循环 :: 调试循环是硬件项目的核心节奏：预测结果、运行观察、对比差异、定位原因、修改一处，五步一圈反复迭代直到达标。:: 生活里的例子 :: 神射手不会连放十箭都闭着眼——每射一箭都看靶调整，才越打越准。
FIG: 一张赛道俯视图：环形黑线上标注了三个危险点位（急弯 A、缓弯 B、窄线段 C），旁边一张五步调试循环图：预测→运行→观察→定位→修改，箭头首尾相连成环 :: 赛场胜负不在零件，而在圈数——谁把调试循环转得又快又多，谁就赢

S: 用数据找到瓶颈
P: 第一轮先跑个基准成绩：用第四章的保守参数完整跑三圈，记录每次总用时和出界次数。假设平均二十五秒、出界一次。别急着改代码，先当侦探分析时间花在哪：分段计时会发现，直道可能只占总路程的一半却几乎不丢分，丢时间的是弯道——冲出去重上线的代价高达五六秒。
P: 定位到瓶颈就可以对症下药。方案一：全程降速保稳定——简单但上限低；方案二：分路段变速——直道全速弯道减速，需要程序按位置切换参数；方案三：优化修正参数让过弯更贴线。正确顺序是先试方案三（零成本），再试方案二（小成本），最后才考虑方案一（牺牲性能）。
CALL: 动手推演 :: 如果你的车在缓弯 B 总是向外冲出半米，列出至少三个可能的原因（传感器高度？速度太快？修正幅度太小？），并设计实验逐一排除。

S: 迭代日志的力量
P: 正式调参前，给每支队伍发一件秘密武器：迭代日志。一张表格五列——第几版、改动内容、预期效果、实际成绩、下一步。每一轮调试填一行。它的价值在半小时后显现：改了七八个参数后，你还能记得哪个改动带来了提升吗？没有日志的队伍会在「改好了还是改坏了」的迷雾里打转。
P: 展示一份真实的日志片段：第七版把弯道速度差从六十降到四十，预期减少出界，实测 24.1 秒无出界，有效，保留；第八版试图直道提速到一百，预期省时，实测 23.8 秒但弯道险些出界，风险高，回退。看懂了吗？每一行都是一次可控的实验——这就是工程师的科研方法。
P: 赛后复盘同样重要：无论名次如何，全队一起回答三个问题——哪一版改动贡献最大？哪个环节浪费了最多时间？下次会换什么策略？把答案写进日志的最后一行。比赛会结束，但复盘出的经验会跟着你进下一场比赛。
P: 比赛日还有一条心理建议：赛前锁定参数。很多队伍临场手痒大改参数，结果把调好的车改坏。正确的赛前姿势是用日志里的最优版本跑三遍确认稳定性，然后封存代码。赛场比的不只是技术峰值，更是稳定输出的下限。
KC: 赛前锁参 :: 比赛日最忌临场大改参数；用迭代日志里的最优版本连跑三次确认稳定后封存代码，稳定输出的下限比技术峰值更决定成绩。:: 试一试 :: 为你的最优配置写一份「封存说明」注明三个关键参数。
CALL: 动手开赛 :: 组队完成一轮完整的竞速挑战：至少十版迭代、完整日志、三次稳定成绩，赛后复盘哪一版改动贡献最大。

S: 全书回顾
P: 五章一场完整的工程旅程：开箱清点建立全局观，齿轮底盘搭出身体，积木程序注入灵魂，传感器赋予感知，赛场的无数次迭代把毛坯磨成利器。你学到的表面上是拼装一辆小车，实际上是「预测—验证—修改」的工程方法论。
P: 这台小车之后，愿你再看任何复杂设备时都会多问一句：它的结构怎么传力？程序怎么决策？出了问题该从哪一步查起？保持动手，保持追问，下一个站上领奖台的队伍就是你的。
