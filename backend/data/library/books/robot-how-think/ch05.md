T: 小项目：设计图书搬运机器人

S: 接单：先听清需求
P: 图书馆王老师提出需求：希望有一台机器人，能把还书车上的书搬到分类台，路上要避开读者，电量不足能自己回去充电。注意，需求不等于方案——「搬书」背后藏着一系列必须追问的细节：一次搬几本？路线固定还是随机？图书馆几点人最多？工程师的第一课就是把模糊的愿望翻译成明确的指标，这道工序叫需求分析。|mark:需求分析
P: 追问之后指标清晰了：载重两公斤、速度不超过每秒半米（安全优先）、避障距离三十厘米、连续工作四小时。每个数字都要有依据：半米每秒是校园里行人速度的一半，撞到人也无大碍；四小时对应一个上午的班次。凭空拍脑袋的参数，日后都会变成事故报告。
CALL: 想一想 :: 如果王老师补充说「周末儿童馆人多且孩子喜欢追着机器人跑」，哪些设计指标需要重新考虑？

S: 选型：为任务配齐三大件
@kp=robot-sensor
P: 感知系统这样配：超声波传感器负责前方测距，三十厘米避障正好在它舒适区；底盘前方加一条碰撞开关做最后保险；循迹用红外对管沿着地面贴好的引导线走——图书馆动线固定，引导线是最省脑子的方案。摄像头这次不上：识别读者不是必需能力，够用原则再次胜出。
P: 决策层用第三章的状态机：待命、取书、送货、返回充电四个状态。送货途中超声波发现障碍就临时切进「礼让」子状态——减速、等待三秒、绕行半米再回主线。执行层选双马达差速转向，转弯半径小，适合书架间窄道；抓取机构简化成带挡板的倾斜托盘，书放上去靠重力固定，比机械手便宜十倍也可靠十倍。
FIG: 设计草图：俯视图上一台方形底盘机器人沿地面虚线引导线行驶，前方画着超声波波束扇面，托盘上立着几本书，右上角状态图小图标显示「取书→送货→返回」循环 :: 一份合格的设计图要让别人一眼看懂：感知在哪、怎么走、装什么
P: 反馈环节安排两处：行驶中红外对管持续修正方向保证压线走；托盘上装一个简易压力开关，确认书上座了才出发，防止空跑一趟。你看，第四章学的「测量—比较—调整」和第二章的多重确认，全都用上了。
KC: 够用原则 :: 选传感器和零件时不必追求最贵最先进，能稳定完成当前任务的就是好选择。省下的成本和复杂度，都是可靠性的来源。:: 生活里的例子 :: 图书馆动线固定，一条贴在地上的引导线比昂贵的摄像头识别更便宜也更可靠。
CALL: 动手挑刺 :: 盯着这套方案找出至少两个潜在漏洞。提示：想想引导线被书车压住怎么办、两位读者的书包同时出现在两侧怎么办。

S: 测试与迭代
P: 方案落地前还有最后一关：测试计划。工程师不会等造好了才试，而是分阶段验证——先空载跑通引导线一周，再加载两公斤复测转弯与刹车距离，然后请志愿者扮演「乱入的读者」做压力测试，最后才进馆试运行。每一阶段都记录失败案例，失败不是坏消息，没被发现的失败才是。
P: 试运行第一周果然暴露了预案外的情况：有同学把饮料瓶放在引导线上，机器人对着瓶子反复礼让不敢过。团队随即给「礼让」状态加了超时规则——同一障碍等待超过十秒就鸣笛请求人工协助。这个补丁很小，却体现了工程的真味：好机器人不是一次设计出来的，是边用边改出来的。
P: 回顾整个项目你会发现，本书四章知识全部各就各位：需求分析用了第一章的循环视角，选型用了第二三章的传感器脾气与状态思想，测试用了第四章的反馈思维。所谓综合应用，不过是让每个零件回到它该在的位置上。
P: 最后留一道开放题：如果要把这台机器人升级成能在没有引导线的图书馆工作，你会怎么改造它的感知与决策？把你的方案讲给别人听——能讲清楚的设计，才是真的想清楚了。
KC: 分阶段测试 :: 新机器人要分阶段验证：先空载跑通基本功能，再加载复测性能，最后请真实用户做压力测试。每阶段的失败都要记录在案。:: 试一试 :: 给「教室值日机器人」列出三个测试阶段各自要验证的问题。
