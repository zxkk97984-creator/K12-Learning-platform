T: 向数据提问：统计三件套

S: 好问题长什么样
P: 「分析一下我的账本」不是好问题，太笼统；「这周一共花了多少」「哪类消费最烧钱」「哪一天失控了」才是好问题——具体、可回答、答案对你有用。数据分析的乐趣九成来自提问：问得越刁钻具体，数据给出的回报越惊人。本章备好三件工具接住你的任何提问。|mark:提问
@kp=descriptive-statistics
KC: 描述性统计 :: 描述性统计用少数几个指标概括一批数据的特征：总和看规模，均值看水平，中位数抗极端值，最大最小值圈出范围。:: 试一试 :: 对同一组工资数据分别算平均数和中位数，比较两者差距说明了什么。
P: 第一件工具是聚合计算。「sum(amounts)」一步求出总花费；配合上一章的清洗流程，总支出、日均支出都是一行代码的事。Python 还内置了 statistics 模块：「from statistics import mean, median」之后，「mean(amounts)」「median(amounts)」各取所需——还记得吗，收入类数据优先看中位数，消费数据同理。
P: 第二件是分组汇总，也是迭代聚合模式的正式登场。想回答「每类花了多少」，就循环每条记录，按类别累加金额。核心只有一行代码：「counts[kind] = counts.get(kind, 0) + amount」，把每条记录的类别作键、金额累加进字典。
P: 这行和第一章计数的骨架完全相同，只是加号后面从 1 换成了金额。跑完之后用 items() 遍历打印，一张「类别小计表」就出炉了。你会再次体会到：数据分析的核心模式少而精，变化的只是装进模式里的字段。
FIG: 一张手绘报表示意：左侧原始流水三十行杂乱排列；中间一个漏斗标「按类别聚合」；右侧输出五行整齐的小计「餐饮 86 元 / 文具 24 元 / 交通 15 元 / 娱乐 40 元 / 其他 9 元」 :: 聚合就是给流水账装上漏斗：三十行进，五行结论出
P: 第三件是找极值与排序。「max(rows, key=lambda r: r["金额"])」直接返回金额最大的那条完整记录——比只拿到数字更有用，因为你知道那天买了什么；「sorted(counts.items(), key=lambda kv: kv[1], reverse=True)」把类别按花费从高到低排队。lambda 是临时小函数的名字，读作「取每条记录的某字段来比」。
CALL: 想一想 :: max 的 key 参数如果换成「len(r["项目"])」，找出来的会是什么？先推理再验证——读懂这个变化，说明你真的理解了排序键的含义。

S: 把三件工具串成一次问答
P: 实战演练三个问题连击。问题一：这周花了多少？——sum 一行解决。问题二：哪天最失控？——先按日期聚合日支出，再对结果取 max，两步合成。问题三：如果每天预算二十元，超支几天？——循环判断大于二十的天数并计数，又是熟悉的聚合变体。
P: 提问质量还体现在对照思维上。「这周花了多少」只有一个答案，「和上周比呢」就有了趋势；「奶茶花了多少」是一个数字，「如果不买奶茶能省多少」就是一个决策依据。好分析师的习惯是把每个问题都配上一面镜子问题，让数字照出变化和选择。
P: 注意这三个问题的共同点：每个都对应一段五到十行的小程序，程序里只有你已经掌握的三样东西——循环、字典聚合、内置统计函数。所谓「会用数据分析问题」，并不是会背多少高深算法，而是能把一个好问题流畅地翻译成这几段小代码。
P: 动手时间：对你的账本提出五个自己的问题并全部实现，其中至少一个是「反直觉猜想」——比如「我猜周末花得比平时多一倍」，用数据证实或推翻它。猜错不要紧，被自己的数据打脸恰恰是数据分析最迷人的时刻：原来我对自己的了解也会出错。
KC: 极值定位 :: 用 max 或 min 配合 key 参数可以直接拿到「最大/最小的那条完整记录」而不只是一个数字，方便继续追问当时发生了什么。:: 试一试 :: 对一周账目找出金额最大的那笔，打印它的日期与项目名。
CALL: 动手挑战 :: 实现「平均每天花多少」时，分母应该用自然天数还是有效记录天数？两种算法结果差多少？哪种更符合你想回答的问题？

S: 小结与预告
P: 回顾本章：提问质量决定分析上限；统计三件套——聚合求总、分组汇总、极值排序——覆盖了日常问题的绝大多数；statistics 模块与 lambda 排序键是你的新词汇；反直觉的答案往往最有价值。
P: 到这里，数字证据已经齐了，但一大串数字的说服力仍然有限——听众需要逐项比较才能感受差距。同样的结论，画成图能让人三秒看懂。下一章不借助任何外部库，就用字符把你的数据画出来。
