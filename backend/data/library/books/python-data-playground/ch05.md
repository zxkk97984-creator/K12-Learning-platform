T: 小项目：一周零花钱账本分析

S: 项目蓝图与数据准备
P: 总装时刻。任务书如下：拿到一份七天的消费流水（CSV），产出一份包含统计结论、分类图表和改进建议的分析报告。这个流程和职业数据分析师接到的需求在结构上一模一样，只是规模不同——把它完整走一遍，你就体验了这门手艺的全貌——这就是我们的毕业项目。|mark:毕业项目
P: 先造数据。按下面的样子准备 账本.csv，也可以换成你自己记录的真实账目（更推荐）：首行表头「日期,项目,类别,金额」，随后每天三到五条记录，类别覆盖餐饮、交通、文具、娱乐，故意埋两处问题——一行金额留空、一行日期写成「周8」。真实感是练习的一部分。
FIG: 项目路线图：五个站点依次为「读取与体检」「统计三问」「聚合画图」「撰写报告」「复盘迭代」，每站旁标注对应章节号，终点是一面小旗写着「报告 v1」 :: 一次完整的分析之旅：五章技能各就各位，串成一条流水线

S: 编码：从读到图的流水线
P: 程序骨架分四段。第一段读取加清洗：DictReader 读入，逐条去空白、尝试转浮点、坏行计入清单，最后打印体检报告「共 N 条，有效 M 条，问题 K 条」。第二段回答三问：总支出、日均支出、最贵的一笔（用 max 加 key 直接拿整条记录）。第三段分组聚合出各类别小计并降序排序。
P: 第四段画图输出：按缩放公式把每类金额变成四十格以内的横条，标注比例尺，附原始数值列。四段代码预计五十到七十行——听起来不小，但每一行你都在前四章亲手写过，这里只是把它们按顺序排好队。遇到卡壳就回到对应章节找原型，这不叫作弊，这叫工程。

KC: 报告三要素 :: 一份合格的数据报告包含结论（数字）、证据（图表）与建议（行动），三者缺一不可；只报数字不给建议的报告只完成了一半。:: 试一试 :: 把「本周餐饮占 46%」翻译成一条具体可执行的建议。
CALL: 想一想 :: 为什么建议把「打印体检报告」放在程序最前面而不是最后？如果坏行悄悄被跳过，最终结论的可信度会发生什么变化？

S: 从结果到洞察
P: 跑通之后，重点来了：读你的结果。假设输出显示餐饮占比过半且周三出现异常高峰（那两颗雷之外的真实模式），先核实异常是数据错误还是真消费——这正是第一章埋的伏笔：区分「数据问题」与「事实发现」是分析师的基本修养。确认无误后，才轮到洞察发言。
P: 洞察要落到建议上。「餐饮占比 46%，其中三次是奶茶」比「要少喝奶茶」有力得多——前者有数据支撑且指向具体行为。好的建议满足三个条件：基于图表中的明确证据、具体到行为而非口号、考虑可行性。试着写出三条这样的建议，每条不超过二十个字。
P: 复盘迭代是最后一站。回看全程：哪个环节耗时最多？（多半是清洗）哪里的代码重复了？（聚合逻辑出现了两次，可以抽成一个函数）如果下个月要做月度版，哪些参数需要改？把这些写进报告附录。第一次项目的价值一半在成果，另一半在这些反思里。
P: 项目做完了还能玩什么？试试给程序加一个命令行参数：输入文件名就能分析任何账本；或者加一个「月度模式」，自动汇总四周数据。每加一个功能，都是对前四章概念的一次复习——游乐园的门票是通票，设施随便玩。
P: 提交前做一次诚实检查：报告里的每个数字都能在代码输出中找到出处吗？图表标注了比例尺吗？建议都有证据链吗？这份自查清单会伴随你的整个数据生涯——它防的不是 bug，而是自欺。
KC: 诚实自查 :: 提交分析报告前的最后一步：核对每个数字有出处、图表有比例尺标注、建议有证据链，防的不仅是 bug 更是自欺。:: 试一试 · 给自己的报告逐项打钩，缺一项就补一项。
CALL: 动手交付 :: 完成报告并与同学交换互评：找出对方报告中一个无出处的数字和一个缺证据的建议。互相挑刺是最快的进步方式。

S: 全书回顾
P: 五章一座游乐园：列表字典教你收纳数据，CSV 打通真实世界，统计三件套替你提问作答，文本图表让结论开口说话，最终项目把一切拧成作品。你收获的不只是几段代码，而是一条完整的思维流水线——提问、取证、计算、呈现、反思。
P: 数据素养的尽头不是技术，而是诚实地面对世界：让数字说话，也听懂数字没说出口的部分。愿你今后每次看到惊人的结论时，都会自然地问一句——数据是怎么来的，又是怎么算的？
