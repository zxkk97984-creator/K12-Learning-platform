T: HTTP 与浏览器的一场对话

S: 一问一答的聊天规则
P: 拿到 IP 地址，浏览器终于可以和网站服务器正面交谈了。交谈用的语言叫 HTTP——超文本传输协议。它的性格极其简洁：永远由浏览器先开口提问（请求），服务器再作答（响应），一问一答，答完即止。网页上的每个资源，背后都是这样一轮或几轮对话。
@kp=http-protocol
KC: HTTP 协议 :: HTTP 规定了浏览器与服务器之间的消息格式：请求包含方法、路径与附加信息，响应包含状态码与内容，双方按此规则逐条交换。:: 生活里的例子 :: 银行柜台的单据规范：客户在申请单写明要办什么，柜员按格式回复并盖章说明办理结果。
FIG: 左右两个对话气泡：左侧浏览器气泡写着「GET /index.html」附三行小字（域名、可接受的格式等）；右侧服务器气泡顶着大大的「200 OK」，下方拖出一页 HTML 代码 :: 一次最简单的 HTTP 对话全貌：请求一行说清来意，响应一个码定调成败
P: 请求的第一行是重头戏。「GET /index.html HTTP/1.1」三个词分别是方法、路径和协议版本。GET 表示「我要取内容」，是最常用的方法；POST 则表示「我要提交数据」，登录表单、发帖评论用的都是它——GET 只读不写，POST 会带来改变，这个区别是 Web 开发的地基常识。
P: 响应的第一行是三位数字的状态码，相当于柜员盖章的办理结果。家族规矩好记：二开头成功（200 最常见），三开头重定向（301 意思是「搬家了，去新地址」，浏览器会自动跟过去），四开头是客户端的错（404 找不到你要的页面），五开头是服务器的错（500 内部出错）。看首数字就能定位责任在哪边。
CALL: 想一想 :: 你输入的网址少打了一个字母，页面却正常打开了——可能发生了什么？提示：想想哪个状态码专门负责「这里没有，去别处找」。

S: 无记忆的协议与补救的甜点
P: HTTP 有个先天特点：无状态。每次请求都是全新的一问一答，服务器转头就忘——你翻到购物车第二页时，它并不记得第一页是你看的。这设计让服务器轻装上阵，却也带来麻烦：登录状态怎么维持？
P: 补救方案是 Cookie：服务器第一次响应时塞给你一张小票，浏览器替你保管，之后每次请求自动出示。凭这张小票，服务器才能认出「还是刚才那位顾客」。理解了这一点，很多现象豁然开朗——为什么清空 Cookie 后所有网站都要重新登录，为什么「记住我」功能本质是给小票延长的有效期。
P: 无状态听起来像缺陷，其实是深思熟虑的取舍。记住每位用户的状态需要海量存储，而大多数请求彼此无关；把状态推给浏览器（Cookie）和专门的数据层，服务器就能轻装接待海量访客。有得必有失，架构设计的艺术正在于选择放弃什么。
P: 动手看看真实的对话。浏览器的开发者工具（多数浏览器按 F12 打开）里有一个网络标签页：刷新任意网页，你会看到几十行请求列表，点开任意一条，请求头、响应头、状态码一览无余。花十分钟逐项观察，比读十篇文章更直观——本章的所有概念都能在里面找到实物。
KC: Cookie :: Cookie 是服务器第一次响应时发给浏览器的小票，浏览器替你保管并在后续每次请求时出示，服务器靠它认出「还是刚才那位访客」。:: 试一试 · 退出登录后再登录一次常用网站，感受小票被重新发放。
CALL: 动手实验 :: 打开开发者工具的网络面板，故意访问一个不存在的路径，找到那个红色的状态码记录；再对比一次成功请求的完整往返耗时，看看时间都花在哪一段。

S: 小结与预告
P: 回顾本章：HTTP 是一问一答的无状态协议；GET 与 POST 分管读取与提交；状态码首位数字快速定性成败与责任方；Cookie 用小票机制补上了记忆缺口；F12 网络面板是随时可开的观察窗。
P: 到这里，一次访问的技术主线已经走通。但还有两个现实问题悬而未决：怎么让全球用户都快起来？以及——对话被第三方偷听了怎么办？最后一章同时回答这两问。
